# 老系统改造的一点想法

> 本文只记录一些通用的项目经验，ps：作者被迫后端转需求，现在是沟槽的FDE，所以有些措辞比较技术。

最近接触的这类项目，把一套用了很多年的老营收系统，慢慢迁到新的技术架构上。老系统是 JSP，新的方向可能是 Spring、Nginx 这一套。

这种项目最重要的一点，不是上来就想着把老系统重新设计一遍，而是先想办法让业务继续用。页面能不动就不动，功能能照搬就先照搬。用户已经习惯了原来的菜单、按钮和操作顺序，没必要为了体现“改造”而强行改变使用习惯。

## 先把需求摸清楚

我的做法一般是先找出最常用、最重要的几个模块，然后一个模块一个模块地看，不能一上来就想把整个系统都弄明白。

先根据菜单、截图、原型图和以前留下的文档，把页面和按钮列出来。接着逐个页面看：查询是干什么的，新增和保存做什么，详情、审核、导出是不是另外一套逻辑。

和业务人员过需求的时候，除了问“这个功能要不要”，还要问几个更实际的问题：

- 这个页面平时是谁在用？
- 主要是为了解决什么事情？
- 页面上的每个按钮实际怎么用？
- 哪些地方不好用，但大家已经习惯了？
- 系统现在的做法，和实际业务有没有对不上？
- 这个页面到底要不要改，还是照原来的来就行？

很多时候，业务人员最后会说：这个页面现在能用，不用改，照搬就行。这个结果其实很好。需求越稳定，迁移越容易，后面也少很多扯皮。

## 不能只看页面名称

老系统里最容易踩坑的，就是页面名称看起来很明白，但实际做的事情不一定是想的那样。所以只看截图和菜单是不够的，还是得回源码里核对。

一般会顺着这条线看：

> 菜单 → URL → Action → JSP → Service 或 JAR → SQL → 表/视图

重点看几个东西：

- 页面到底查了什么；
- 保存时真正写了什么；
- 状态值分别代表什么；
- 日期条件用的是哪个字段；
- 统计的是用户、地址、表具，还是一条业务记录；
- 页面查询和导出是不是同一个口径；
- 查询、保存和后续处理是不是一条链。

这些东西不看清楚，需求文档写得再漂亮，迁移以后也可能对不上。

看完源码后，再把里面的类名、字段名和 SQL 条件翻译成业务人员能看懂的话，写成“需求描述”和“操作说明”。技术细节可以作为分析依据，但正式文档没必要全是代码名称。

另外，分析结论最好分清楚：哪些是源码已经确认的，哪些只是根据代码推测的，哪些还要找业务或现场再问。尤其是老系统，能在源码里找到，不代表生产环境一定就是这么跑的。

## 需求没过完，也不能一直等

这类项目通常周期比较紧，需求可能一直在确认，开发又不能一直停着。所以实际做的时候，往往只能边开发、边过需求、边验证。

比较稳妥的办法是：

1. 已经明确不需要改的页面，先按老系统迁过去；
2. 还没确认的地方，先尽量保持原样，不自己发挥；
3. 迁移过程中把不确定的地方记下来，后面集中找业务确认；
4. 确认有变化的，再单独作为需求变更处理。

有老系统源码的话，AI 可以帮忙读代码、找调用关系、整理页面功能和生成迁移初稿，效率会高一些。但它只能帮忙整理，不能代替源码核对和业务确认。尤其是账号、客户信息、内网地址、生产数据这些东西，使用前必须先脱敏，能不提供完整源码就不要提供完整源码。

## 关于进度和汇报

项目没法等所有需求都确认完再开始，所以进度汇报可以按模块和阶段来讲。比如：源码分析完成、页面迁移完成、联调完成、业务确认完成、还有哪些待确认。

这几个状态最好不要混在一起。一个模块代码迁过去了，不等于需求已经确认；页面能打开，也不等于数据口径已经验证。后面如果业务提出调整，就记录成需求变更，说明原来迁移了什么、现在要改什么。

这样既能让项目有进展，也不会把“已经迁移”和“已经验收”混为一谈。

## 最后

老系统改造其实不是简单地把旧代码换个技术栈。真正麻烦的是，既要保住原来的业务，又要慢慢把不清楚的规则、历史问题和新需求理顺。

我觉得比较实用的顺序就是：

> 先看页面，问清业务；再看源码，搞清规则；能照搬的先照搬；有变化的单独记；最后再逐项确认和优化。
